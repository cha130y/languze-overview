# Contract test coverage

Which behavior of the NestJS API the contract tests pin, file by file of its end-to-end suite (`apps/api/test`). Those files test the Nest application from inside, so they cannot judge the ASP.NET Core port (ADR-0006); each behavior they lock has to reach a contract test before its slice is ported, or be listed below as covered another way.

`/port-slice` fills this table: for each `it(...)` in the slice's e2e files, the contract test that covers it, or why none can.

Each test class carries a `Slice` trait with a name from the table, such as `[Trait("Slice", "Auth")]`. `pnpm test:contract --target dotnet` runs only the slices listed in `PORTED_TO_DOTNET` in `scripts/run-contract-tests.mjs`, which so far are Platform, all of Auth, Users and Worlds: sign-up, sign-in, sign-out, `GET /v1/me`, verifying an email address, resetting a password, signing in with Google, LINE and Facebook, the Terms step after a provider sign-in, deleting an account, and creating, reading, renaming and deleting worlds, removing a word and retrying an analysis. Blocked photos, the pauses they earn and the timeout check have no endpoint of their own and are covered in process. A slice ported in parts lists its operations rather than its paths, and its tests still waiting for .NET carry a trait of their own until then.

## Covered another way

- **The origin secret.** `pnpm test:contract` starts the API without one, as local development runs, so a black-box test cannot see it refuse. `through-cloudflare.e2e-spec.ts` covers NestJS, and `LanguZe.Api.Tests/Platform/PipelineTests` covers .NET, both with a secret set: a request without it is refused even as a preflight, and Railway's healthcheck host is let through.

- **Rate limits before a route has one.** `platform.e2e-spec.ts` tests the limiter on a probe route only the test registers: RATE_LIMITED with `Retry-After`, counting per account or per forwarded address, and ignoring an address a caller claims without a trusted proxy. `LanguZe.Api.Tests/Platform/RateLimitPipelineTests` does the same for .NET, and `RateLimitStoreTests` checks what no black-box test can wait for: a block lasting a whole window from the request that went past the limit. `RateLimitTests` pins the real routes' limits against NestJS now and against .NET from the authentication slice on.

- **Accounts in states only an admin or a provider sign-in leaves.** Until the admin slice is ported, no black-box test can suspend an account, and only a provider sign-in leaves one waiting for the Terms. `auth.e2e-spec.ts` does both through Prisma; `LanguZe.Api.IntegrationTests/AccountTests` does the same in process, on a database of its own: signing in to a suspended account is `ACCOUNT_SUSPENDED` and ends its sessions, a suspended account's session is refused even on `/health`, an account waiting for the Terms reaches `GET /v1/me` and nothing else, and a pause on the AI features shows in `aiAccess` until it is lifted. It also signs in with a password Better Auth hashed, as every password is at cutover.

- **The Terms step and the sweep of sign-ups left waiting.** `LanguZe.Api.IntegrationTests/TermsStepTests` signs in with a fake LINE or Facebook, which leaves an account waiting for the Terms, as `auth.e2e-spec.ts` builds one through Prisma: accepting opens the account with the name and year given, a year under 18 leaves it waiting, and declining removes it with its provider link and sessions (US-004 criteria 1 to 3). With a clock it moves, the sweep removes a sign-up left waiting fifteen minutes and nothing else, reads the database only while a provider sign-up may be waiting, and watches from the start for one a previous process left, as `pending-sign-up-cleanup.service.spec.ts` checks; `LanguZe.Api.Tests/Auth/PendingSignUpCleanupTests` checks that it runs on the clock's five minutes, as the cron expression does. Declining's limit of ten a minute is set as in NestJS but cannot be reached from outside: declining signs the browser out, and a request without a session is not counted.

- **What deleting an account takes from the database.** `account-deletion.e2e-spec.ts` reads it through Prisma; `LanguZe.Api.IntegrationTests/AccountDeletionTests` does the same in process: the account goes with its sessions and provider sign-ins and leaves other learners alone, every photo of the account leaves a cleanup record (`ACCOUNT_DELETED`), and a row of each kind of learner data written with SQL into the tables of slices not yet ported (worlds, words, XP, tutor messages, blocked photos, AI suspensions) goes by the cascades Prisma's schema declares.

- **Photo storage and its cleanup.** Storage has no endpoint of its own: `photo-storage.e2e-spec.ts` tests the S3 adapter against SeaweedFS, and so does `LanguZe.Api.IntegrationTests/PhotoStorageTests`: a stored photo comes back through its signed link byte for byte, the link carries a signature and an expiry, a tampered link is refused, a removed photo is gone, and removing one already gone is content. `PhotoCleanupTests` covers what `photo-cleanup.service.spec.ts` checks with fakes: a sweep removes each due object and then its record, a record whose object could not be removed waits a minute and the rest carry on, the schedule sweeps at startup and then only once a record is expected or while a postponed one remains, and deleting an account sets it looking. `LanguZe.Api.Tests/Storage` ports `photo-preparation.service.spec.ts` (the 2,048-pixel limit, the thumbnail, the camera orientation applied, every piece of metadata dropped, the accepted formats) and the cleanup's timings.

- **Creating a world, where only the database shows it.** `LanguZe.Api.IntegrationTests/WorldCreationTests` checks what `worlds.e2e-spec.ts` and `analysis.e2e-spec.ts` read through Prisma: the stored photo is the prepared one at 2,048 pixels with a 320-pixel thumbnail, and only it reaches the provider, safety check first; each AI call is recorded with its cost and the ID of the request that caused it; each failure of the fake provider (an error, a timeout, too few words, nothing usable) fails the world and gives the analysis back; a word found in two worlds is one word; the twenty-first world is `WORLD_LIMIT_REACHED`; and the eleventh analysis of a Bangkok day is `DAILY_ANALYSIS_LIMIT` with nothing stored, while failed ones do not count.

- **Deleting a world, removing a word and retrying.** `LanguZe.Api.IntegrationTests/WorldEditTests` checks what the e2e files read through Prisma or a failing fake: deleting a world leaves a cleanup record (`WORLD_DELETED`) for each of its photos and removes their rows; it takes the words nothing else has, with their mastery and mistakes (US-014 criterion 3), and keeps those another world has; removing a word deletes it only with its last occurrence (FR-027); a failed world keeps its photo, and a retry that goes well makes it READY; a retry once today is used up is `DAILY_ANALYSIS_LIMIT` and leaves the world failed; and a world whose photo was removed cannot be retried.

- **A blocked photo, the pause it earns, and an analysis that never finished.** The contract run's fake provider allows every photo, so `LanguZe.Api.IntegrationTests/PhotoBlockTests` checks what `analysis.e2e-spec.ts` reads through Prisma and a blocking fake: a blocked photo leaves no stored photo and a cleanup record (`PHOTO_BLOCKED`) for each file, records its block, fails the world as `BLOCKED` without asking for words, counts toward the day, and cannot be retried; the third block in seven days pauses the AI features for a week, the threshold after an earlier pause and one photo of suspected illegal material wait for an admin, older blocks and other learners' are not counted (V15, FR-098); while paused, a new photo is `AI_SUSPENDED` with when it ends and a retry runs nothing, while worlds stay readable (US-092); and a pause waiting for an admin is emailed to every active admin, or to `ADMIN_ALERT_EMAIL` while there is none, without naming the learner, never for a pause that ends by itself, and a mail server that refuses leaves the pause in force (FR-107). `StaleAnalysisTests` covers V16: an analysis older than five minutes is released with its world, a young one and a world that finished another way are left alone, and the minute check reads only from an analysis's start, or the API's, until it must have ended. `LanguZe.Api.Tests` ports `suspension-rules.spec.ts` and the check's timings.

- **The Gemini adapter.** Gemini is never called by a test. `LanguZe.Api.Tests/Ai/GeminiAiProviderTests` ports the photo half of `gemini-ai-provider.spec.ts` against a stand-in for the SDK: the verdict and its category, a category LanguZe does not know as `OTHER`, Gemini's own refusal as a block, the safety model asked with the photo and fixed instructions only, an answer with no verdict refused; extraction's boxes turned from Gemini's 0 to 1000 into LanguZe's fractions, a misshapen item passed on for the rules to refuse, an answer with no list refused, a refusal during extraction as a provider error; a call past its deadline as `TIMED_OUT`, any other failure as `PROVIDER_ERROR`, an empty answer and one that is not JSON refused; and the model for each job. It also pins the SHA-256 of each instruction as `prompts.ts` words it, since the AI evaluation judged those words, and that the C# SDK's retries and automatic continuation are off, as the JavaScript SDK's are. The tutor half comes with the tutor slice. `AiModuleTests` checks that a key chooses Gemini.

- **How long a session lasts.** Seven days, renewed for seven more when it is used a day or more after it was issued: Better Auth's `expiresIn` and `updateAge`, which no test of NestJS's checks. No black-box test can wait a week, so `LanguZe.Api.IntegrationTests/SessionTests` moves a clock in process.

- **Verification links over time, and email that cannot be sent.** No black-box test can wait an hour or stop Maildev for one request, and NestJS's suite tests neither. `LanguZe.Api.IntegrationTests/VerificationTests` runs the API in process with a clock it moves and a mail transport that keeps or refuses what it is given: a link works until an hour has passed, as Better Auth's `expiresIn` sets it; sign-up and asking again both succeed when the email cannot be sent, as Better Auth logs the failure rather than failing the request; and a link whose account has gone since is `INVALID_TOKEN`, as in NestJS, whose account deletion takes Better Auth's reset row with it, as NestJS answers Better Auth's `USER_NOT_FOUND`.

- **Reset links over time, and the accounts a reset cannot reach.** `LanguZe.Api.IntegrationTests/PasswordResetTests` runs the API in process, as for verification: a reset link works until an hour has passed, an account without a password is emailed no link (US-007 criterion 3), a link whose account has gone since is `BAD_REQUEST`, and asking for a reset answers the same when the email cannot be sent.

- **A Google sign-in from start to finish.** No black-box test can sign in at Google, and NestJS's suite does not either: it calls Better Auth's adapter directly (`account-linking.e2e-spec.ts`). `LanguZe.Api.IntegrationTests/GoogleSignInTests` starts a sign-in through the API, comes back with the state it made, and answers the Google handler's backchannel with a fake Google: a first sign-in opens an account that waits for the Terms and keeps no provider token (D3); one seen before signs in to its account; joining an account whose address was never verified takes away its password and its sessions, while a verified one keeps both (US-004 criterion 6, U6); an address Google has not verified joins nothing (FR-009); and a code Google refuses goes back to the sign-in page. `LineAndFacebookSignInTests` does the same with fakes of LINE and Facebook: a first sign-in opens an account with a placeholder address (D1), which `GET /v1/me` shows as none while the AI features unlock (V13, V14); one seen before signs in to its account; neither ever joins an account by address, Facebook not even with the address of an existing account in its answer (US-005 criterion 3); and no provider token is kept (D3). A real round trip waits for the cutover rehearsal, since Google, LINE and Facebook know only production's callback addresses.

## Known differences

Behavior where the two APIs differ on purpose, or where NestJS does something no client relies on.

- **The message of an unreadable body.** NestJS answers malformed JSON, or a body that is `null`, a number or a string, with the JSON parser's own message, such as `Unexpected end of JSON input`; the .NET API says `The request body could not be read.`. Both answer `BAD_REQUEST`, which is what `RequestValidationTests` pins.
- **A lone surrogate in a string**, such as `"\ud83d"`: JavaScript keeps it, and NestJS judges the field as usual; .NET cannot hold it in a string, so the body is `BAD_REQUEST`. No form can send one.
- **The latest year of birth.** NestJS works out `@Max(new Date().getFullYear())` once, when the process starts, so a process running across New Year keeps the old year; the .NET API reads the clock each time. Both refuse a year after the current one in every other case.
- **Other reset links, once a password is set.** Better Auth keeps each reset link as a row and deletes only the one used, so a second link asked for earlier still works until it expires. The .NET API's links name the account's security stamp, which setting a password changes, so every other reset link of the account stops working too (ADR-0006, section 5). The requirements ask only that a link work once and expire (UC-004), and a reset may follow a leaked password (S7). `PasswordResetTests.Setting_a_password_ends_every_other_reset_link_of_the_account` pins it.
- **Starting a provider sign-in with an ID token.** Better Auth's `POST /auth/sign-in/social` also signs in with an ID token the caller already holds, when the body carries `idToken`. The .NET API leaves that branch out and starts a redirect sign-in whatever the body says: the web app never sends one, and ADR-0006 leaves a mobile app's authentication to a decision of its own. `disableRedirect`, `scopes`, `loginHint`, `additionalParams` and `requestSignUp` are ignored for the same reason.
- **A provider name Better Auth does not know.** Better Auth checks the name against its list of every provider it supports and answers one outside it with 400; one on the list without credentials, such as `github`, is 404 `PROVIDER_NOT_FOUND`, which `AuthProviderTests` pins. The .NET API knows only LanguZe's providers and answers 404 `PROVIDER_NOT_FOUND` for any other name. A body that is not a JSON object with a `provider` is 400 on both, the message may differ.
- **Where a sign-in's state is kept.** Better Auth writes a `verifications` row for each sign-in started, with a signed cookie; the .NET API keeps the state in the protected `state` parameter and a correlation cookie, as ASP.NET Core's handlers do, and writes nothing. A browser sees the same: a sign-in lasts ten minutes, and coming back without its cookie is `state_mismatch`.
- **The password reset left behind by a deleted account.** NestJS deletes the row Better Auth keeps for a reset the learner never used. The .NET API keeps no such row, since its reset link names the account; once the account is gone the link is `INVALID_TOKEN` in both, which `AccountDeletionTests.A_reset_link_asked_for_before_the_deletion_no_longer_works` pins.
- **An answer from Gemini that is JSON `null`.** NestJS reads a property of it and throws a `TypeError`, so the analysis fails as `PROVIDER_ERROR` and the call is recorded with the code `TypeError`. The .NET API reads it as an answer with no verdict, or no list of items, so the analysis fails as `INVALID_OUTPUT`. Either way the analysis fails and is given back; Gemini cannot answer `null` to a request whose schema asks for an object.
- **Releasing lost analyses at startup.** NestJS releases them before it answers its first request, and a database it cannot reach then stops it from starting. The .NET API releases them while it starts answering, and logs a database it cannot reach, as it does for a failed minute check, so the API still starts. A learner whose world was lost in a restart sees it fail a moment later at most.

## Fixed in NestJS during the port

What the port found and fixed in `apps/api` first, each in a pull request of its own (CLAUDE.md), so the .NET API reproduces the fixed behavior.

- **Unknown paths outside `/v1`** (2026-10-28). NestJS mounts its not-found handler under the global prefix only, so `POST /health`, `GET /` or any other path outside `/v1` that no route matched got Express's HTML "Cannot POST" page. `NotFoundFallback` now answers them with `NOT_FOUND` in the error format, as the .NET API does; `PlatformTests` pins both cases.
- **An address only Better Auth refuses, at sign-up** (2026-10-29). Better Auth throws two kinds of APIError, its own and better-call's, which its own extends and which a refused request body raises. `AuthService` checked `instanceof` its own, so an address validator.js accepts and Better Auth refuses, such as `élève@example.com` or one on a Thai domain, escaped as a 500 at sign-up while sign-in answered `BAD_REQUEST`. It now uses Better Auth's `isAPIError`, which knows both. `AuthTests.An_address_better_auth_refuses_is_BAD_REQUEST` and an e2e test in `auth.e2e-spec.ts` pin it.
- **A reset link for an account without a password** (2026-10-29). US-007 criterion 3 asks that an account signing in only through a provider see the same message and receive no reset link. Better Auth sends one to any account it finds by address, and opening it gives that account a password it never had. LINE and Facebook accounts are spared by their placeholder addresses (D1); a Google account is not. Found by reading Better Auth's source while planning the port, not by a test. `createAuth` now sends nothing when the account has no password, leaving Better Auth's token and timing alone, and an e2e test in `auth.e2e-spec.ts` pins it. No contract test can reach it until the providers slice, since a password-less account cannot be made over HTTP before then; the .NET API reproduces it, as `PasswordResetTests` checks in process.
- **A name the database cannot hold, at the Terms step** (2026-10-30). `isLength` counts a heart with its variation selector once, and the `varchar(50)` column counts two code points, so a name of 50 such characters passes the DTO and breaks the column.
