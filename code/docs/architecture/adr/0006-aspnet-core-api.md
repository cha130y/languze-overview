# ADR-0006: Port the API to ASP.NET Core

- **Status:** Accepted, 2026-10-28, once the first contract tests passed against the NestJS API (section 3)
- **Date:** 2026-10-28
- **Related:** [ADR-0001](0001-modular-monolith.md), [ADR-0002](0002-toolchain-baseline.md), [ADR-0003](0003-better-auth-in-api.md), [ADR-0004](0004-ai-provider.md), [ADR-0005](0005-postgresql-and-pgvector.md); [data model](../data-model.md) (D1, D3, D5); [API design](../api-design.md); [production deployment](../../deployment/production.md); [launch checklist](../../deployment/launch-checklist.md)

## Context

Release 1.0 was released on 2026-10-27 (tag `v1.0.0`) with the API on NestJS 12, Prisma 7.10 and Better Auth 1.7.5 (ADR-0002, ADR-0003). The operator will now rewrite the API in C# on ASP.NET Core.

The reason is the operator's direction, not a fault in the current API: the roles the operator is aiming for use C#, and C# is the language the operator wants to work in. Performance is not a reason. Production's `ai_calls` for the 30 days to 2026-10-28 show where the time goes: the safety check at p95 2.5 s, extraction at p95 3.6 s, and each tutor call at p95 2.3 s, all spent waiting for Gemini. A faster runtime would not change what a learner waits for.

What the port keeps:

- The requirements, the domain tables of the data model, and the API contract the web app uses
- The web app (Next.js), which keeps generating its types from the API's OpenAPI document
- The deployment: Cloudflare (DNS, Access, the origin secret), Railway, Neon, R2, Resend, and Gemini on a paid key

What it has to respect:

- Existing learners keep their accounts, their learning data and their passwords
- Signing out, a password reset (FR-005) and a suspension (FR-105) end sessions at once, as they do now
- The current end-to-end tests cannot check the new API: all 21 files build the Nest application in the test process and reach into its providers, so they test this implementation, not the contract

## Options considered

| Option                                                                      | For                                                                                                                | Against                                                                                                                              |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Keep NestJS                                                                 | No work, nothing at risk                                                                                           | Does not meet the goal                                                                                                               |
| A new project from scratch                                                  | Free of every earlier decision                                                                                     | Throws away finished requirements, data model, web app and deployment; takes longest                                                 |
| Port, keeping every table including Better Auth's (package 1)               | No data migration; learners stay signed in                                                                         | The .NET API has to reproduce Better Auth's session, cookie and token formats by hand, and keep matching a library it no longer runs |
| **Port, keeping the domain tables, with ASP.NET Core Identity (package 2)** | Authentication on the framework's own, maintained system; the domain schema and every foreign key stay as they are | The authentication tables are reshaped once at cutover; every learner signs in once more; outstanding email links stop working       |

## Decision

Port the API to ASP.NET Core, package 2.

### 1. Runtime and layout

- **.NET 10**, the current LTS release, supported until 2028-11-14 (SDK 10.0.403 on 2026-10-28, from Microsoft's release index), pinned in `global.json`. Pins and their reasons go into ADR-0002 when it is rewritten for .NET (section 8).
- The new API lives in `apps/api-dotnet` beside `apps/api` until cutover. `apps/api` is then removed; git keeps its history.
- The module boundaries of ADR-0001 carry over as they are: auth, users, worlds, vocabulary, learning, progress, tutor, ai, moderation, notifications, storage. Auth and users keep NestJS's split exactly (the account endpoints stay in auth), so each file has one counterpart.

**Code structure** (decided 2026-10-28, after three reviews against the NestJS code):

- **Minimal APIs**, which Microsoft recommends for new projects; **no MediatR**: an endpoint calls its handler through dependency injection, and MediatR is under a commercial licence from version 13.
- **Request bodies are checked by rule attributes of the API's own** (`Platform/Validation`), named after class-validator's decorators and written on a request record in its DTO's order: `[property: IsEmail, MaxLength(254), IsDeliverableAddress] string Email`. They run on the JSON before it becomes the record, as NestJS's ValidationPipe runs before the handler. A body is read as Express's JSON parser reads one, and every broken rule is answered under class-validator's name, in its order. validator.js's `isEmail`, `isFQDN` and `isLength` are ported and checked against answers validator.js gives itself. This replaced the first plan, DataAnnotations with .NET 10's built-in validation, on 2026-10-29. DataAnnotations check a record after the JSON has bound to it, so a value of the wrong type, a missing body or a `text/plain` one fails before any rule runs, where NestJS answers `VALIDATION_FAILED`, and a year sent as `"1990"` is refused where NestJS converts it.
- **One project, a modular monolith with vertical slices inside each module.** Each module is `Modules/<Module>/` with `Features/<Slice>/` (endpoint, request and response records, handler; one slice per endpoint), `Domain/` (pure rules, as answer-check.ts and mastery-rules.ts are now; a transaction script with pure rules, not DDD aggregates), `Shared/` (what the module's slices share), `Jobs/` (background services), and `Contracts/` (what other modules may call). `Platform/` holds what every module uses; `LanguZe.Tools`, a console project, will hold promote-admins, the load-test seed and the AI evaluation.
- **Entities are shared**, scaffolded into `Data/Entities` and used through one `LanguZeDbContext`, the way every NestJS module uses one Prisma client. Which module owns a table is the module it is listed under in the [data model](../data-model.md), section 4, and the places that write another module's table are listed in section 4.9.
- **Architecture tests** (ArchUnitNET, `LanguZe.Api.Tests/Architecture`) keep the boundaries the compiler cannot, since the modules share a project. R1: `Domain` depends on no framework and no database. R2: a slice depends on no other slice. R3: a module reaches another only through its `Contracts` (entities excepted). R4: an endpoint never touches the database. R5: `Platform` knows no module. Each rule was shown to fail on a deliberate violation, including one made only inside a method body, before it was trusted.
- **The way to a separate service**, should ADR-0001's reasons for one ever arise, is one module at a time: first make it own its tables inside the monolith, replacing reads of other modules' tables with their `Contracts` and dropping cross-module foreign keys, with the contract tests proving nothing outside changed; only then move it out, turning its `Contracts` calls into HTTP or messages. Splitting the data and the transactions that span modules (account deletion, suspension) is the hard part, and is not paid for in advance.
- **Background work keeps its cost behavior.** The analysis runs in the background as it does now, and the stale-analysis check skips the database while no analysis is running, which is what lets Neon's compute sleep ([production deployment](../../deployment/production.md), section 10). Losing that would spend Neon's monthly compute in two weeks.

### 2. Order of work

1. **Contract tests first** (section 3). They pass against the NestJS API before any .NET code is written.
2. **Skeleton:** health check, configuration that refuses development defaults in production, the error format, the origin-secret check with its health-check exception, rate limiting, the OpenAPI document.
3. **Authentication slice** (section 5), since almost every other endpoint needs a signed-in learner.
4. **The remaining slices**, in the order of the [build plan](../../planning/build-plan.md). Each one is done when its contract tests pass against both APIs.
5. **AI evaluation** re-run through the .NET adapter before cutover, by ADR-0004's rule for any change in how models are called.
6. **Cutover** (section 5, last part), once the browser smoke tests (`pnpm test:browser`) also pass with the web app talking to the .NET API: the contract suite checks HTTP, and only a browser shows that cookies, CORS, the origin check and the tutor's stream work for the real web app.

### 3. Contract tests

Black-box HTTP tests that run against a base URL and know nothing of either implementation: status codes, response bodies, error codes, cookie attributes, security headers and rate limits. Emails are read from Maildev's HTTP API, and the AI runs through the fake provider both APIs offer when no key is set.

Written in **C# with xUnit**, in `tests/api-contract`. The suite outlives NestJS and becomes the .NET API's acceptance suite, so it is written in the language the API will be maintained in, and it is the first C# in the repository, where a mistake costs least. TypeScript with Vitest was the alternative: faster to start with the existing tools, but it would leave a TypeScript test project guarding a C# API.

`pnpm test:contract` starts the API under test and runs the suite (xUnit v3 on Microsoft.Testing.Platform, the runner .NET 10's `dotnet test` expects). The API runs with one trusted proxy hop, so each test stands for its own caller through `X-Forwarded-For`; otherwise the per-address limits, such as five sign-ups an hour, would make the tests trip over one another. The first 16 tests, on health, security headers, the error format, the origin check, accounts and sessions, and the sign-up limit, passed against NestJS on 2026-10-28. With `--target dotnet` the same suite runs against the .NET API, limited by each test class's `Slice` trait to the slices ported so far.

### 4. Data access

- **EF Core with Npgsql.** The existing schema is adopted as it is, a slice at a time: a slice that reads a table adds its entity to `Data/Entities`, matched to the table Prisma created, with a migration that changes nothing because the table already exists. The first was `Baseline`, for the authentication tables. From cutover on, EF Core migrations own the schema. Table and column names stay in snake_case, keys and indexes keep Prisma's naming (`Data/SchemaNames.cs`), and IDs stay UUID version 7 (D5). A unit test fails when the model changes without a migration.
- **A database of its own until cutover.** The NestJS API keeps `languze`, and the .NET API runs on `languze_dotnet` on the same PostgreSQL, likewise in CI, and on staging's own Neon project (production deployment, section 17). Its schema is Prisma's migrations followed by EF Core's (`pnpm db:dotnet`). Chosen on 2026-10-28 over two alternatives. Identity's stores written over the Better Auth tables would have kept one database, at the cost of rewriting much of Identity. Adding Identity's tables to production through Prisma would have changed production's schema before cutover.
- **The cutover migration is written first.** `ReshapeAuth` (section 5) was written in the first authentication slice, so every CI run applies it to a new database, and integration tests (`LanguZe.Api.IntegrationTests`) run it on accounts written in Better Auth's shape and run it back. The rehearsal on a copy of production is its last run, not its first.
- Prisma's `_prisma_migrations` table is dropped at cutover; the migrations themselves stay in git history.
- pgvector, when RAG arrives (ADR-0005), through `Pgvector.EntityFrameworkCore` (MIT; its README states support for EF Core 9 and 10). Prisma 7.10 has no vector type: `@db.Vector` fails validation, and only `Unsupported("vector(…)")` with raw SQL works.

### 5. Authentication

ASP.NET Core Identity replaces Better Auth.

| Area               | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Reason                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| User table         | Identity's user maps onto `users`, keeping each learner's ID, so every foreign key in the domain stays                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | D5                                                                                                             |
| Sessions           | Cookie authentication with the session kept in PostgreSQL through a ticket store, so signing out, a password reset and a suspension end it at once. 7 days, renewed daily while used, as now                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | FR-005, FR-105, NFR-019                                                                                        |
| Cookie             | `HttpOnly` and `SameSite=Lax`; `Secure` and the `__Secure-` prefix whenever `AUTH_URL` is HTTPS, as in production, which is Better Auth's own rule; domain from `COOKIE_DOMAIN` (`.languze.com` in production). Named `__Secure-languze.session` (`languze.session` locally), unlike Better Auth's, so an old cookie is simply ignored                                                                                                                                                                                                                                                                                                                                                                                                            | A1, H5                                                                                                         |
| Existing passwords | Better Auth stores `salt:key` in hex: scrypt with N=16384, r=16, p=1 and a 64-byte key, over the NFKC-normalized password, with the salt's hex text as the salt (read from `@better-auth/utils` 0.4.2, the version Better Auth 1.7.5 resolves; 0.5.0's password code is the same). `BetterAuthPasswordHasher` verifies that format and answers "rehash needed", so Identity rewrites the hash in its own format at the learner's next sign-in. Its scrypt is `BouncyCastle.Cryptography` 2.7.0 (MIT), checked against hashes Better Auth wrote                                                                                                                                                                                                    | Learners keep passwords                                                                                        |
| Providers          | Google and Facebook through Microsoft's handlers; LINE through `AspNet.Security.OAuth.Line` (aspnet-contrib, Apache-2.0, maintained by the community, not Microsoft). Google confirmed 2026-10-30 (`Microsoft.AspNetCore.Authentication.Google` 10.0.14): `POST /auth/sign-in/social` answers the handler's address as JSON, as Better Auth does, and a callback ends where Better Auth's ends, with its words in `?error=`. LINE and Facebook confirmed the same day (`AspNet.Security.OAuth.Line` 10.0.0, `Microsoft.AspNetCore.Authentication.Facebook` 10.0.14): LINE asks for `openid profile` with PKCE, and Facebook for `public_profile` on Graph API v24.0 without PKCE, as Better Auth 1.7.5 does, where both handlers' defaults differ |
| LanguZe's rules    | Linking only on a provider-verified email, removing the password and sessions of an unverified account it joins, placeholder emails, clearing provider tokens, the Terms step with its 15-minute cleanup, the age check, and suspension are written again, each with the contract test that pinned it in NestJS                                                                                                                                                                                                                                                                                                                                                                                                                                   | FR-009, D1, D3, FR-090, V20                                                                                    |
| Keys               | ASP.NET Core Data Protection keys are kept in PostgreSQL, so cookies survive a redeploy, encrypted there with AES-256-GCM under `DATA_PROTECTION_KEY`, which only the environment holds. A copy of the database therefore cannot forge a session cookie, as one of NestJS's cannot without `AUTH_SECRET`. Losing or changing the key signs every learner out and changes nothing else                                                                                                                                                                                                                                                                                                                                                             | Railway's disk is not kept; DPAPI is Windows only, and a certificate would be a file to renew for one instance |
| Email links        | The token in each emailed link is protected by Data Protection with its expiry, an hour on, as Better Auth's links last; Better Auth's `verifications` table is not recreated. A verification token names the address and works until it expires, as Better Auth's signed one does. A reset token names the account and its security stamp, so setting the password ends it and every other reset link with it, where Better Auth deletes only the one used. The requirements ask only for single-use links that expire (UC-004)                                                                                                                                                                                                                  | No schema change; the stricter reset links follow S7                                                           |

**Cutover.** One migration moves the data, `ReshapeAuth` (section 4), rehearsed last on a copy of production:

- `users` keeps every row and ID and gains Identity's columns. Each `auth_accounts` row for a password becomes the hash on its user, still in Better Auth's format. Each provider row becomes a `user_logins` row under the same provider name
- It stops if an email address is not ASCII: Identity finds an account by its upper-cased address, which .NET and PostgreSQL's `upper()` agree on only for ASCII
- `sessions` and `verifications` are not carried over: every learner signs in once more, and a verification or reset link that is still open stops working, so the learner asks for another
- The old authentication tables are renamed `better_auth_sessions`, `better_auth_auth_accounts` and `better_auth_verifications`, their keys and indexes with them, and kept for 14 days. The migration's `Down` renames them back, so the switch can be undone by running it and pointing `api.languze.com` back at the NestJS service. A password changed through the .NET API in between is lost that way, and an account created through it has no Better Auth password. A later migration drops them
- `sessions` starts again as the ticket store, and `user_logins`, `user_claims`, `user_tokens` and `data_protection_keys` are new

**A mobile app** is not planned. If one comes, its authentication is its own decision: Identity's bearer tokens last an hour by default and cannot be ended at once, which FR-005 as written does not allow.

### 7. Deployment

No provider changes. The .NET API ships as a container to the same Railway service; Cloudflare, the origin secret, `TRUST_PROXY_HOPS`, Neon, R2 and Resend stay as they are. Until cutover it runs as a staging service of its own, in a Railway project and a Neon project apart from production's (production deployment, section 17). Moving to another cloud is not part of this decision and would have its own ADR.

### 8. Documentation

While the port runs, the documents describe what is running. At cutover, ADR-0002 and ADR-0003 are rewritten as the .NET decisions they become rather than superseded, and the README, architecture overview and production guide follow. Git history keeps the NestJS record.

### 9. How the port is worked: an AI harness

From here on, development leans on AI coding agents, and the port suits them: most of it reproduces behavior that is already written, specified and tested. An agent's work is only as trustworthy as the checks around it, so the checks come first:

- **The contract suite decides.** A slice is ported when its contract tests pass against both APIs, not when the code looks right, and the agent runs them itself before it reports.
- **The two OpenAPI documents are compared.** NestJS already writes `apps/api/openapi.json`; the .NET API serves its own at `/openapi/v1.json` in Development, and `pnpm test:contract --target dotnet` reports any difference on the paths of the slices ported so far, so a renamed field or a missing status code shows up before review.
- **One slice per branch and pull request**, small enough to read, naming the requirements and the NestJS module it reproduces.
- **The project instructions follow the code.** `CLAUDE.md` gains the .NET commands and rules; a skill describes how to port one slice (read the NestJS module, its tests and its requirements; write the contract tests; implement; run both suites; update the documents); the backend agent learns .NET; a hook formats each C# file as it is written, while building, the unit tests and the architecture rules run in `dotnet test` and CI, too slow for every edit.
- **The harness comes in its own pull request**, after this ADR and before the contract tests, so it is in place for the first line of the port.
- **Each slice's pull request says what the checks caught**, so whether the harness earns its keep is recorded rather than assumed.

## Consequences

- During the port the repository holds two APIs and two toolchains. CI runs both, and the contract suite is the gate for each slice.
- Learners notice the cutover once: they sign in again, and any open email link has to be requested again. Their passwords and learning data are untouched.
- Dependency audits cover both ecosystems: `pnpm audit` for the web app and `dotnet list package --vulnerable` for the API.
- The places most likely to break are the ones Release 1.0 already learned the hard way: account linking (FR-009), the Terms step, provider callbacks, the cookie across subdomains (H5), rate limits keyed on the forwarded address, and the Gemini adapter, which must send Gemini's turn back exactly as it came or tool calls fail (ADR-0004).
- The NestJS API stays deployable until the 14 days after cutover have passed, which is what makes the switch reversible.
